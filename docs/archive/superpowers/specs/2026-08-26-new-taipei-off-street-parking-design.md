# 雙北路外停車場兩階段擴充設計

## 目標

在不改變既有推薦邏輯、不中斷臺北市服務的前提下，將「台北停車地獄雷達」擴充為臺北市與新北市路外停車場查詢工具。

第一階段先完成可穩定自用及公開查詢的雙北版本；第二階段必須等待新北資料累積至少 7 天，才加入跨城市分析、資料品質與 Dashboard 功能。

## 成功條件

- 既有「台北車站」查詢結果與排序行為不得退化。
- 使用者可用地址、地標、城市及行政區查詢新北市路外停車場。
- 新北市 API 故障不得阻斷臺北市資料收集或查詢。
- 新北 TWD97 座標必須可靠轉為 WGS84 後才能參與距離與地圖計算。
- 每個城市獨立判斷資料新鮮度，不得由另一城市的新資料掩蓋過期狀態。
- 第一階段沿用既有推薦規則、圖卡、步行路線、導航與七天歷史。
- 第二階段的排名與比較只使用已達最低樣本量的資料。

## 資料來源

### 臺北市

沿用目前兩份官方 JSON 與既有解析器：

- 靜態停車場資料：`TCMSV_alldesc.json`
- 動態剩餘車位：`TCMSV_allavailable.json`

### 新北市

- 靜態資料集：`b1464ef0-9c7c-4a6f-abf7-6bdf32847e68`
- 動態資料集：`e09b35a5-a738-48cc-b0f5-570b67ad9c78`
- OpenAPI：`https://data.ntpc.gov.tw/api/v1/openapi/units/1130000`

新北靜態欄位映射：

| 官方欄位 | 統一欄位 |
|---|---|
| `ID` | `source_lot_id` |
| `AREA` | `district` |
| `NAME` | `lot_name` |
| `ADDRESS` | `address` |
| `PAYEX` | `fee_info` |
| `SERVICETIME` | `service_time` |
| `TW97X`、`TW97Y` | 轉換後的 `longitude`、`latitude` |
| `TOTALCAR` | `total_spaces` |
| `SUMMARY` | 場站型態判斷來源 |

新北動態資料使用 `ID` 與靜態資料連接，`AVAILABLECAR` 為汽車剩餘車位。負數值代表特殊或無法提供狀態，不寫入數值快照。

## 整體架構

```text
collector.py（排程入口）
├─ TaipeiSourceAdapter
└─ NewTaipeiSourceAdapter
        ↓
統一 ParkingLot / ParkingSnapshot 字典契約
        ↓
database.py
        ↓
既有 analysis.py、walking_service.py、fee_service.py
        ↓
Flask API → PWA 圖卡、地圖、導航、歷史
```

來源轉接器只負責下載、驗證、欄位正規化與座標轉換。推薦服務不得知道原始官方欄位名稱。

## 資料模型

### `parking_lots`

新增：

```sql
city VARCHAR(20) NOT NULL
source VARCHAR(20) NOT NULL
source_lot_id VARCHAR(64) NOT NULL
```

並新增：

```sql
UNIQUE KEY uq_lots_source_id (source, source_lot_id)
INDEX idx_lots_city_district (city, district)
```

既有臺北資料 migration 後設定：

```text
city = 臺北市
source = taipei
source_lot_id = 現有 lot_id
```

新北內部 `lot_id` 使用 `NTP:<官方 ID>`，例如 `NTP:010056`。既有 `TPE0001` 不改主鍵，避免重寫歷史外鍵。

### `parking_snapshots`

維持既有結構，由 `lot_id` 關聯 `parking_lots`，不重複保存城市。

新北動態 API 沒有每筆可靠的官方更新時間時：

- `captured_at` 保存系統取得時間。
- `source_updated_at` 同樣保存取得時間。
- API 回應與前端標示為「系統取得時間」，不得稱為官方資料時間。

### Analytics

第一階段不改 Analytics schema。第二階段在 `analytics_query_details` 增加可空的 `city`，並在新事件寫入；不強制回填舊資料。

## 第一階段：雙北可用版

### 城市設定

新增單一城市設定模組，集中管理：

- 城市正式名稱與可接受別名。
- 行政區集合。
- 官方資料來源名稱。
- 地理邊界驗證範圍。
- 功能旗標。

不得在 `app.py`、`ai_service.py`、`geocoder.py` 與 `static/app.js` 各自維護不同版本的行政區清單。

### 新北資料收集

- 靜態與動態端點皆支援分頁。
- 使用有限 timeout，每頁最多重試兩次。
- 重試仍失敗時記錄來源失敗，不覆蓋既有有效資料。
- 新北與臺北各自開啟連線與交易；一個來源失敗時另一個仍可提交。
- 靜態資料最多每日重新抓取一次。
- 動態資料沿用每 15 分鐘收集週期。
- 同一回應出現重複 ID 時，以明確且可測試的去重規則處理並記錄數量。
- 動態 ID 找不到對應靜態場站時跳過快照並記錄數量，不建立缺少總車位與座標的半套場站。

### 座標轉換

新北 `TW97X`、`TW97Y` 使用 EPSG:3826，輸出 WGS84 EPSG:4326。

- 使用單一、經測試的轉換函式或成熟座標函式庫。
- 測試必須使用手工固定的已知座標與容許誤差。
- 轉換失敗、缺值或超出雙北合理範圍時，座標保存為 `NULL`，不得參與附近推薦或地圖標記。
- 不以逐筆 Nominatim 查詢取代批次座標轉換。

### 查詢 API

手動與 Gemini 解析結果統一包含：

```text
city
district
address
arrival_time
```

- 指定行政區時必須同時確定城市。
- 地址已有城市時，以地址城市為準並驗證行政區一致性。
- 只有地標時，由候選地址決定城市。
- 無法唯一判斷時回傳最多三個候選，不自行猜測。
- 查詢完整地址時，可同時比較目的地 1.5 公里內兩市場站，不因行政邊界排除真正較近的場站。
- 手動行政區查詢只查選定城市與行政區。

### 推薦規則

不新增新北專用評分：

1. 排除無效、過期、無座標及超過搜尋範圍的資料。
2. 剩餘不超過 3 格列為不建議前往。
3. 剩餘不超過 10 格或空位率低於 10% 列為備選。
4. 其他場站列為可以前往。
5. 可以前往者優先，再依步行時間排序。
6. 安全場站不足才補入備選。

OpenRouteService 仍只處理最多 15 座候選，失敗時退回直線距離。

### 前端

- 手動表單新增城市選擇。
- 行政區選項依城市切換。
- 地址模式允許跨市附近搜尋。
- 目的地、場站圖卡與資料時間顯示城市及資料來源。
- 頁尾同時標示臺北市與新北市官方資料來源。
- 原有 PWA、語音輸入、地圖、Google Maps 導航與歷史按需載入行為維持不變。

### 費率與場站型態

- 保存 `PAYEX` 完整原文。
- 現有解析器只在格式明確時產生每小時費率與上限。
- 無法確認平假日、上限或車種時顯示未知並保留原文。
- 以新北 `SUMMARY` 的明確關鍵字判斷平面、地下、立體、機械或混合。
- 第一階段不擴大 Overpass 查詢範圍。

### 歷史保留

- 圖表仍顯示最近 7 天。
- 排程每天分批刪除超過 8 天的 `parking_snapshots`。
- 清理失敗不得影響 collector 與公開查詢。
- 清理測試涵蓋 cutoff、commit、rollback 與 close。

### 第一階段發布策略

新增 `NEW_TAIPEI_ENABLED` 功能旗標：

1. 先套用可重複執行的 additive migration。
2. 部署程式但保持旗標關閉。
3. 收集新北資料，驗證場站數量、座標、行政區、費率與有效快照比例。
4. 執行臺北完整回歸測試及新北 smoke test。
5. 開啟旗標，才讓前端顯示新北市。

關閉旗標時只隱藏新北查詢與停止新北收集，資料可保留以便重新啟用。

### 第一階段驗收

- 「台北車站」行為與既有版本一致。
- 「板橋車站」可取得新北附近場站、步行時間、費率與導航。
- 「新北市政府」不會被解析為臺北市政府。
- 臺北與新北同名或模糊地標會要求選擇。
- 新北 API timeout 不影響臺北 collector 提交。
- 臺北新鮮、新北過期時顯示各自狀態。
- TWD97 固定座標轉換測試通過。
- migration 可重複執行。
- 關閉旗標後既有臺北服務正常。
- 七天歷史在 8 天資料清理後仍完整。

## 第二階段：完整雙北分析版

第二階段只有在新北有效快照累積至少 7 天後才開始啟用分析功能。

### 城市與行政區分析

- 臺北、新北分開顯示行政區停車壓力排行。
- 每筆結果顯示有效場站數、樣本數與資料時間。
- 未達最低有效場站數或歷史樣本數時顯示樣本不足，不產生精確排名。
- 不把兩市行政區直接混成單一平均分數。

### Dashboard

新增城市維度：

- 查詢量、成功率及回饋。
- 行政區與目的地分布。
- 解析、地址搜尋、停車查詢及步行路線耗時。
- 各官方來源最後成功時間、timeout 次數與無效資料比例。
- 新北費率及場站型態的已知／未知比例。
- 快照總量、每日新增量及清理結果。

Dashboard 不新增 IP、精確手機位置、Cookie、Authorization 或 API 金鑰紀錄。

### 費率解析改善

- 先分析第一階段累積的真實 `PAYEX` 格式頻率。
- 只實作高頻且能以固定 fixture 測試的格式。
- 分離臨停、月租、機車與小型車資訊。
- 支援格式明確的平日、假日、計時費率及當日上限。
- 不為單一場站新增名稱特例。
- 不可可靠解析時仍以官方原文為準。

### 場站型態補強

來源優先序固定為：

```text
manual > official > osm > unknown
```

- 第二階段才擴大新北 Overpass 範圍。
- 只補官方無法判斷的場站。
- 名稱與距離同時符合才接受 OSM 匹配。
- OSM 不推斷機械式停車場。
- 匹配來源與未知比例在 Dashboard 可見。

### 第二階段驗收

- 新北至少累積 7 天有效快照後才顯示歷史排名。
- 樣本不足不顯示精確分數或名次。
- Dashboard 可分城市查看查詢、效能、來源健康與資料品質。
- 費率解析使用匿名化官方原文 fixture 覆蓋高頻格式。
- 每日快照清理完成後七天圖表仍完整。
- 第一階段全部回歸測試持續通過。

## 錯誤與降級策略

| 失敗 | 行為 |
|---|---|
| 新北靜態 API 失敗 | 保留現有基本資料，本次不更新 |
| 新北動態 API 失敗 | 保留舊快照並標示過期，不寫入假資料 |
| 單頁分頁失敗 | 整個來源本次不提交，避免半套資料 |
| TWD97 轉換失敗 | 場站可保存，但不參與距離與地圖推薦 |
| Gemini 失敗 | 沿用手動查詢 |
| Nominatim 模糊 | 回傳最多三個候選 |
| OpenRouteService 失敗 | 退回直線距離並標示 |
| 清理工作失敗 | rollback 並記錄，不影響查詢與收集 |

## 測試策略

### Characterization

實作前先鎖定目前臺北行為：

- 臺北 collector 欄位與特殊值。
- 台北車站查詢、推薦與導航。
- 臺北行政區手動查詢。
- 費率、歷史與資料時間。

### 第一階段新增測試

- 新北靜態、動態 fixture 解析。
- 分頁、timeout、重試、去重與半套失敗 rollback。
- TWD97 已知座標轉換。
- `city/source/source_lot_id` migration 與 SQL 參數化。
- 雙北地址、行政區、地標候選與城市衝突。
- 城市連動前端、來源標示與 PWA cache 更新。
- 跨市附近搜尋與同規則排序。
- 每城市 freshness 與功能旗標。
- 8 天快照清理交易。

### 第二階段新增測試

- 城市 Analytics 寫入與舊事件相容。
- Dashboard 城市篩選、樣本門檻與 bounded queries。
- 新北高頻費率 fixture。
- OSM 匹配優先序與距離限制。
- 快照量、清理與來源健康彙整。

所有測試離線執行，不在 CI 呼叫臺北、新北、Gemini、Nominatim、OpenRouteService 或 Overpass 真實 API。

## 工程量與程式碼預算

### 第一階段

- 5～8 個工作天。
- 正式程式增加 400～650 行。
- 測試增加 350～550 行。
- 約 3 個新程式檔、1 個 migration、2 份 fixture。
- 修改約 8～10 個既有檔案。

### 第二階段

- 3～5 個工作天。
- 正式程式增加 250～400 行。
- 測試增加 200～350 行。
- 以現有 Dashboard、fee service 與 metadata service 擴充，不另建服務。

若任一階段超過上述上限，必須先檢查是否加入未核准功能或將來源特例散落到共用模組。

## 明確不在範圍

- 路邊停車格。
- AI 空位預測。
- 全臺灣資料。
- 會員、登入或付款。
- 個別民營停車業者爬蟲。
- 新北專用推薦公式。
- 每個停車場的人工費率特例。
- 導航或路線規劃演算法。
- 原生 iOS／Android App。

## 設計原則

- 城市差異留在來源轉接器與城市設定中，共用推薦流程不得分叉。
- 所有 migration 採 additive、可重複執行，回滾程式時保留新欄位及資料。
- 來源失敗採保留舊資料與明確標示，不以空集合覆蓋有效資料。
- 不猜測費率、場站型態、官方時間或地址。
- 第一階段先證明雙北查詢可用，第二階段才對真實歷史資料做比較。
