# 《停車地獄雷達》設計規格

## 1. 專題定位

正式名稱：**《停車地獄雷達：臺北市即時停車難度、歷史分析與智慧推薦系統》**

本系統不是一般的停車場目錄，而是回答三個決策問題：

1. 我現在或預計抵達某地時，附近有多難停？
2. 哪些停車場比較值得前往，哪些應該避開？
3. 平日、週末與不同時段的歷史停車難度有何差異？

使用者可以輸入地址、地標、行政區及抵達時間。Gemini 只負責理解自然語言，實際停車資料、分數與推薦結果全部由 Python、MySQL 和固定公式產生。

## 2. 成功展示情境

使用者輸入：「我今晚六點要去臺北市信義區忠孝東路五段 7 號。」

系統完成以下工作：

1. Gemini 解析出地址、信義區及 18:00。
2. Nominatim 將地址轉為經緯度。
3. 系統找出目的地 1.5 公里內且資料有效的停車場。
4. 系統比較即時空位、距離與相同時段的歷史難度。
5. 畫面顯示目前地獄指數、抵達時段歷史參考、前三名推薦及避雷停車場。
6. 使用者可繼續詢問：「週末晚上通常呢？」系統沿用上一個目的地回答歷史分析。

## 3. 範圍

### 3.1 必做功能

- 取得臺北市停車場靜態資料與即時剩餘車位。
- 納入官方資料中的停管處與非停管處停車場。
- 清洗靜態與動態兩份資料並以停車場 ID 串接。
- 每 30 分鐘將有效即時資料保存到 MySQL。
- 計算停車場及行政區地獄指數。
- 依地址搜尋 1.5 公里內的停車場。
- 顯示距離最近、最推薦、小心前往與應該避開的停車場。
- 以 Gemini 3.5 Flash 理解推薦、歷史與平週末比較問題。
- 使用 Nominatim 進行免費地址轉座標並快取結果。
- 顯示一張 Leaflet 地圖及一張歷史折線圖。
- 提供 Gemini 或地址服務失效時的手動查詢表單。
- 本機可完整展示，並以 GCP 1 vCPU／1 GB Linux VM 為部署目標。

### 3.2 明確不做

- 雙北整合、全臺灣或路邊停車格。
- 個別民營業者網站爬蟲或封閉 API。
- 導航、道路距離、車程、即時定位及路線規劃。
- 天氣、活動、車流量及 AI 空位預測。
- 登入、會員、永久聊天紀錄及管理後台。
- 國定假日 API；歷史資料只分平日與週末。
- 開放式聊天、AI 產生 SQL 或由 AI 自行決定停車數字。
- Docker、Cloudflare Workers 或多機部署。
- 多張分析儀表板及自動清除舊快照。

## 4. 系統架構

核心資料流程：

```text
臺北市靜態資料 ─┐
                 ├─→ collector.py → 清洗 → MySQL
臺北市即時資料 ─┘

使用者問題 → Gemini 結構化解析 ─┐
                                ├─→ Python 固定分析函式 → 單頁結果
地址 → Nominatim → 經緯度 ──────┘
```

模組職責：

- `app.py`：Flask 路由、請求驗證、工作流程協調及頁面輸出。
- `config.py`：從環境變數讀取資料庫、Gemini 及應用程式設定。
- `collector.py`：下載、清洗及保存臺北市停車資料。
- `database.py`：集中處理 PyMySQL 連線與固定 SQL 查詢。
- `analysis.py`：地獄指數、距離、推薦分數及歷史統計。
- `ai_service.py`：Gemini 結構化輸出及三種意圖判斷。
- `geocoder.py`：Nominatim 查詢、使用限制及地址快取。
- `templates/index.html`：唯一主頁。
- `static/style.css`：深色與橘紅警示視覺。
- `static/app.js`：表單、對話、Leaflet、圖表及結果更新。
- `schema.sql`：三張資料表及索引。
- `tests/test_core.py`：核心純函式測試。

每個模組只負責一件主要工作。應用程式不建立額外的 controllers、repositories 或多層抽象。

### 4.1 技術棧

- 後端：Python、Flask、PyMySQL、Pandas。
- 資料庫：MySQL。
- 前端：HTML、CSS、JavaScript。
- 圖表與地圖：Chart.js、Leaflet、OpenStreetMap 圖磚。
- 外部服務：Gemini 3.5 Flash、Nominatim、臺北市資料大平臺。
- 執行與版本管理：Linux、Git；部署目標為 GCP Linux VM。

## 5. 資料來源

主要來源為臺北市資料大平臺「臺北市停車場資訊」：

- 靜態資料：停車場 ID、行政區、名稱、地址、營運類型、總車位、費率、開放時間及座標。
- 動態資料：停車場 ID、剩餘汽車車位、官方更新時間及替代停車場 ID。

官方資料頁：<https://data.taipei/dataset/detail?id=d5c0656b-5250-4179-a491-c94daa56ef2c>

`TYPE2 = 1` 表示停管處經營，`TYPE2 = 2` 表示非停管處經營。系統可以顯示兩者，但不宣稱涵蓋所有民間停車場。

## 6. 資料庫

### 6.1 parking_lots

保存可更新的停車場基本資料：

- `lot_id`：官方停車場 ID，主鍵。
- `lot_name`、`district`、`address`。
- `operator_type`：停管處或非停管處。
- `total_spaces`。
- `fee_info`、`service_time`。
- `latitude`、`longitude`。
- `supports_realtime`。
- `source_updated_at`、`updated_at`。

### 6.2 parking_snapshots

保存每次取得的即時事實：

- `snapshot_id`：自動流水號，主鍵。
- `lot_id`：外鍵，連至 `parking_lots`。
- `available_spaces`。
- `source_updated_at`：官方資料時間。
- `captured_at`：系統抓取時間，統一存 UTC。

建立 `(lot_id, captured_at)` 查詢索引，並以 `(lot_id, source_updated_at)` 唯一限制避免重複快照。

### 6.3 geocode_cache

保存 Nominatim 已解析的地址：

- `normalized_address`：標準化地址，主鍵。
- `display_address`。
- `latitude`、`longitude`。
- `cached_at`。

系統不保存地獄指數、推薦分數或聊天內容，因為前兩者可重新計算，聊天只需要短期工作階段狀態。

## 7. 資料清洗

只有符合以下條件的資料能參與數值計算與推薦：

- `total_spaces > 0`。
- `0 <= available_spaces <= total_spaces`。
- 經緯度存在且合理。
- 即時資料距目前時間不超過 45 分鐘，對應每 30 分鐘蒐集一次並保留 15 分鐘緩衝。

臺北資料中的 `-9`、`-11`、`-12`、`-13` 是特殊狀態，不是負的停車位。這些資料可顯示對應文字，但不參與需要精確格數的分數及排行。

下載或寫入失敗時，該次蒐集不新增半套快照，網站繼續使用資料庫中最近一次成功資料並顯示最後更新時間。

## 8. 計算規則

### 8.1 單一停車場地獄指數

```text
使用率 = (總車位 - 剩餘車位) / 總車位
地獄指數 = 使用率 × 100
```

分級：

- 0～59：輕鬆停。
- 60～79：開始擠。
- 80～94：很難停。
- 95～100：停車地獄。

### 8.2 行政區地獄指數

行政區採車位數加權，不直接平均各停車場：

```text
行政區地獄指數 = 全區已使用車位總數 / 全區有效總車位數 × 100
```

### 8.3 距離

目的地與停車場使用 Haversine 公式計算直線距離。只保留 1.5 公里內的候選停車場，不計算道路距離或車程。

### 8.4 推薦分數

三個子分數都換算為 0～100，越高代表越值得前往：

- 即時容易度：`100 - 即時地獄指數`。
- 距離容易度：目的地為 100 分，1.5 公里為 0 分，中間線性遞減。
- 歷史容易度：`100 - 相同日別與時段的歷史地獄指數`。

歷史樣本足夠時：

```text
推薦分數 = 即時容易度 × 50% + 距離容易度 × 30% + 歷史容易度 × 20%
```

歷史樣本不足時：

```text
推薦分數 = 即時容易度 × 60% + 距離容易度 × 40%
```

系統顯示前三名推薦。最近停車場與最推薦停車場分開列出，避免把距離最近誤解為最有機會停到。

## 9. 歷史分析

- 每 30 分鐘保存一次有效即時資料。
- 資料庫以 UTC 儲存，查詢與畫面轉成 `Asia/Taipei`。
- 星期一至星期五為平日，星期六與星期日為週末。
- 歷史時段以整點小時分組。
- 至少三筆有效樣本才顯示歷史參考，畫面同時顯示樣本數。
- 歷史折線圖只顯示目前選定停車場最近七天的空位變化。
- 行政區摘要可以顯示最難停時段及平日／週末差異，不增加第二張圖。

歷史結果統一稱為「歷史參考」，不稱為 AI 預測。

## 10. Gemini 對話

Gemini 3.5 Flash 只輸出固定結構資料，不直接推薦停車場。允許三種意圖：

1. `recommend`：依地址、行政區及抵達時間推薦。
2. `history`：詢問行政區或停車場的歷史趨勢。
3. `compare`：比較平日與週末。

結構至少包含：意圖、原始目的地、地址、行政區、抵達時間及是否缺少必要資訊。行政區必須限制為臺北市十二個行政區之一。

Flask 工作階段只記住上一個目的地、行政區、停車場與抵達時間，供「那週末呢？」等簡單追問使用；不建立聊天資料表。

Gemini 不得：

- 產生或執行 SQL。
- 自行填入剩餘車位、距離或歷史分數。
- 回答停車分析以外的一般問題。
- 在必要條件不足時假裝完成查詢。

Gemini 無法使用、回傳格式錯誤或等待逾時時，畫面提示使用手動行政區及時間表單；核心分析仍能使用。

## 11. 地址搜尋與地圖

地址解析使用 OpenStreetMap Nominatim 公共服務，遵守以下限制：

- 先查 `geocode_cache`，相同地址不重複請求。
- 每秒最多一個請求。
- 提供可辨識本專題的 User-Agent。
- 不製作輸入時自動完成。
- 畫面標示 OpenStreetMap 貢獻者。
- 查不到地址時請使用者修正地址或改選行政區。

Leaflet 地圖只顯示：

- 目的地標記。
- 候選停車場標記。
- 依推薦狀態使用綠、黃、橘、紅顏色。
- 點擊標記顯示名稱、距離、剩餘車位及狀態。

不加入導航、路線或道路圖層分析。

## 12. 單頁介面

頁面由上往下依序為：

1. 標題、資料最後更新時間。
2. Gemini 對話輸入及手動查詢入口。
3. 目的地、目前地獄指數及抵達時段歷史參考。
4. 最推薦、小心前往、不要去了三類結果卡片。
5. Leaflet 地圖與距離最近清單。
6. 一張歷史折線圖及文字摘要。
7. 臺北市資料、OpenStreetMap 標示與歷史參考免責文字。

介面採深色背景搭配橘紅警示色，手機版改為單欄排列。專題不建立第二個一般使用者頁面。

## 13. 最小錯誤處理

- 外部 HTTP 請求設定合理逾時，失敗時顯示簡單明確訊息。
- 官方資料失敗時使用最後成功資料。
- Gemini 失敗時使用手動表單。
- Nominatim 失敗時改用行政區查詢。
- 資料庫失敗時顯示服務暫時無法使用，不回傳堆疊資訊。
- 所有使用者輸入在進入 SQL 前必須驗證，SQL 使用參數化查詢。
- Gemini 金鑰、資料庫密碼與 Flask 密鑰存於環境變數，`.env` 不提交 Git。

專題不加入每 IP 限流、複雜重試框架、監控後台或自動告警。

## 14. 測試

自動測試集中在 `tests/test_core.py`，至少覆蓋：

- 負數、缺值及剩餘車位超過總車位的清洗。
- 單一停車場與行政區加權地獄指數。
- Haversine 距離與 1.5 公里篩選。
- 50／30／20 推薦公式。
- 歷史不足時的 60／40 公式。
- 歷史最少三筆樣本規則。

外部 API 使用固定範例資料或模擬回應，不讓自動測試依賴即時網路。另保留一份簡短人工展示清單，確認手動表單、Gemini、地圖、圖表及失敗備援。

## 15. GCP 部署

部署目標為 GCP 免費額度可用的 1 vCPU／1 GB Linux VM：

```text
Nginx → Gunicorn（1 worker）→ Flask → 同機 MySQL
```

部署原則：

- Ubuntu Server，無桌面環境。
- 建立 1～2 GB swap。
- MySQL 限制記憶體並只監聽 localhost。
- Linux cron 每 30 分鐘執行 `collector.py`。
- API 金鑰與密碼使用環境變數。
- 不使用 Docker。
- 本機版必須維持可執行，GCP 不是發表成功的單一依賴。

部署設定寫入 README，不另外建立雲端控制程式。

## 16. 程式規模與註解

- 約 13 個主要檔案。
- 程式本體含繁體中文註解目標為 1,500～2,000 行，硬上限 2,500 行。
- 單一程式檔案盡量不超過 250 行。
- 單一函式盡量不超過 30 行。
- 每個檔案開頭說明用途。
- 每個函式說明功能、輸入與輸出。
- 關鍵清洗、公式、SQL 與例外處理加上繁體中文註解。
- 不為顯而易見的每一行重複撰寫無意義註解。

若功能會突破規模上限，刪除順序為：地圖額外互動、非必要文字摘要、視覺動畫。歷史分析、核心推薦、地址查詢與手動備援不可刪除。

## 17. 驗收條件

完成版本必須符合：

- 可成功取得並保存臺北市靜態與動態停車資料。
- 可排除負數、過期及不合理即時資料。
- 可依行政區手動查詢，不依賴 Gemini。
- 可依一筆臺北市地址找出 1.5 公里內候選停車場。
- 可顯示地獄指數、前三名推薦、最近及避雷結果。
- 可在歷史樣本足夠時顯示抵達時段參考與一張折線圖。
- Gemini 可處理三種限定意圖與一次簡單追問。
- Gemini 或 Nominatim 失效時，核心查詢仍可使用。
- 本機環境可完整展示。
- 核心測試通過，程式維持既定規模及繁體中文註解標準。
